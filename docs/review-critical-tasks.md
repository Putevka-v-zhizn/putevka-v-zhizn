# Задачи по итогам ревью — 2026-10-09

Проверены код приложения и конфигурация запуска. Приоритеты отражают риск для развёрнутого сервиса. Наличие уязвимости на конкретном сервере зависит от его переменных окружения; они в рамках ревью не проверялись.

## P0 — убрать создание администратора с известным паролем

**Факт:** `entrypoint.sh:52-65` при каждом старте создаёт суперпользователя `admin`, если его нет, с паролем по умолчанию `0000`.

**Риск:** новая инсталляция или восстановленная БД доступна через известные учётные данные до ручной смены пароля.

**Исправление:** убрать создание администратора из обычного запуска. Сделать отдельную одноразовую команду и требовать явно заданный сильный пароль; для уже развёрнутых экземпляров проверить учётную запись `admin`, сменить пароль и завершить её активные сессии.

**Готово, когда:** запуск с пустой БД не создаёт суперпользователя; создание без явно заданного пароля завершается ошибкой; проверка существующих инсталляций задокументирована.

## P0 — запретить предсказуемый SECRET_KEY в рабочем окружении

**Факт:** `Putevka/settings.py:31`, `docker-compose.yml` и `docker-compose.qa.yml` используют запасное значение `local-dev-insecure-secret-key`.

**Риск:** при пропущенной переменной ключ подписи Django известен публично; это ставит под угрозу подписанные данные и токены.

**Исправление:** требовать `SECRET_KEY` при `DEBUG=false`, удалить запасное значение из compose, добавить проверку длины и уникальности ключа при развёртывании. Если инсталляция уже работала со стандартным ключом, заменить его и инвалидировать выданные токены/сессии.

**Готово, когда:** сервис не стартует в рабочем режиме без ключа или со стандартным ключом; конфигурационный тест покрывает оба случая.

## P1 — ограничить потребление памяти при загрузке файлов

**Факт:** `Putevka/settings.py:195-200` оставляет только `MemoryFileUploadHandler` и разрешает до 250 МБ на файл. `entrypoint.sh:74` запускает веб-сервер без отдельного ограничения параллельности/памяти на уровне приложения.

**Риск:** несколько одновременных загрузок могут исчерпать память процесса или контейнера и остановить сервис.

**Исправление:** использовать временные файлы для крупных загрузок, установить предел тела запроса на прокси и в приложении, задать лимиты по типам файлов и ресурсам контейнера. Проверить очистку временных файлов при ошибке загрузки на Яндекс Диск.

**Готово, когда:** допустимый крупный файл не удерживается целиком в памяти; запрос сверх лимита отклоняется до обработки; параллельный тест загрузки укладывается в установленный лимит памяти.

## P1 — перейти с Django runserver на рабочий WSGI-сервер

**Факт:** `entrypoint.sh:72-74` содержит закомментированный запуск Gunicorn и реально запускает `manage.py runserver`; тот же entrypoint используется в Dockerfile и compose.

**Риск:** рабочий сервис зависит от сервера разработки, у которого нет управляемых рабочих процессов, таймаутов и штатного graceful shutdown для такой нагрузки.

**Исправление:** запускать Gunicorn с явным числом workers, таймаутами и обработкой сигналов; вынести фонового обработчика уведомлений в отдельный сервис, чтобы он не стартовал повторно вместе с веб-процессом.

**Готово, когда:** контейнер запускает Gunicorn как основной процесс; остановка контейнера корректно завершает запросы и воркер; проверена отправка уведомлений после перезапуска.

## P1 — закрепить защиту HTTPS и сессионных cookie

**Факт:** в `Putevka/settings.py` не заданы `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_SSL_REDIRECT` и HSTS; при этом приложение принимает заголовок `X-Forwarded-Proto` (`:48-49`).

**Риск:** при ошибке настройки прокси сессионные или CSRF-cookie могут уходить по HTTP. Отсутствует дополнительная защита от перехода на HTTP.

**Исправление:** включить secure-cookie и перенаправление HTTPS для рабочих окружений, настроить доверие к proxy headers только за контролируемым прокси. HSTS включать после проверки всех доменов и поддоменов.

**Готово, когда:** `manage.py check --deploy` не сообщает об этих настройках; HTTP перенаправляется на HTTPS; cookie имеют флаг Secure.

## P2 — убрать изменение шага регистрации через GET

**Факт:** `core/views.py:286-297` принимает GET и POST в `skip_telegram`, и оба метода меняют `current_step`.

**Риск:** переход по ссылке, превью или сторонняя страница могут незаметно пропустить шаг регистрации у вошедшего пользователя.

**Исправление:** разрешить изменение только POST с CSRF; GET должен лишь отображать подтверждение или перенаправлять без записи. Обновить ссылки в шаблонах на форму.

**Готово, когда:** GET не меняет состояние, POST с CSRF меняет шаг, POST без CSRF отвергается.
