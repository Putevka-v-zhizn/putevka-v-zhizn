# Развитие MCP: модели, обезличивание и сравнение текстов

Основное подключение, экспорт случаев и локальный импорт описаны в
[инструкции MCP](development-mcp.md). Эти инструменты используются разработчиком
локально. Они не меняют рабочие записи или решения по участникам.

## 3. Черновик новой модели одной командой

В окружении Django выполнить:

```powershell
.\.venv\Scripts\python.exe manage.py draft_mcp_model scholar_form.UserInfo --program main --output .tmp/userinfo-draft.py
```

Вместо `scholar_form.UserInfo` указать свою новую `app.Model`. Без `--output`
черновик выводится в консоль. Папка для файла должна существовать; существующий
файл не перезаписывается. Команда читает действующие поля Django, включая
наследование от абстрактных моделей, и не выполняет SQL-запросов. Многотабличное
наследование и нестандартный первичный столбец требуют ручного описания.
Отключённые поля, переопределённые
через `field = None`, в предложение не попадают.

Черновик содержит `Table`, `Load`, предполагаемые поля `output`, словари
`identities`, возрастную группу и подходящие `CaseFilter`. Для связи с участником
предпочитаются `user` и `target_user`. Если подходящих родителей несколько,
указать `--via <имя_поля>`; направление можно ограничить повторяющимся `--program`.
Без ограничения предлагается связь, доступная хотя бы в одном направлении;
остальные направления не получают недостижимые данные.

Пароли, токены, технические ошибки, файлы, URL, внешние/уникальные идентификаторы,
произвольные JSON-пакеты и даты не предлагаются как выходные поля. Возможные имена,
контакты и адреса предлагаются как словарь очистки. Классификация по именам полей
эвристическая: проверить черновик, необходимые связи и комментарии `Excluded`
перед добавлением в `development_mcp/schema.py`. Например, `first_name` предлагается
как `person`; если это имя самого участника, можно выбрать `participant`.

После добавления декларации выполнить валидатор, тест с контрольными данными,
сгенерировать `grants --update` и сделать MCP-деплой. Генератор не применяет код,
не открывает доступ к новым данным и не меняет PostgreSQL-права.

## 4. Контроль качества обезличивания

В окружении с `development_mcp/requirements.txt`:

```powershell
python -m development_mcp.redaction_quality --output .tmp/redaction-quality.json
```

По умолчанию используется версионируемый синтетический набор
`development_mcp/redaction_cases.json`: русские имена и склонения, общая фамилия
родителя и участника, контакты, скрытые Unicode-символы, ссылки, документы,
реквизиты, адреса, даты и имя на границе блока NER.

Отчёт содержит:

- Долю полностью закрытых размеченных вхождений идентификаторов.
- Точность по размеченным буквам и цифрам: насколько заменённые символы совпали
  с разметкой. Пробелы и пунктуация не влияют на эту метрику.
- Долю сохранённых контрольных фраз, сумм и содержательных фрагментов.
- Индексы пропущенных аннотаций, ошибки и время обработки по случаю.
- Версию правил, хеш реализации, хеш корпуса и версии Python/Natasha/pymorphy3/NumPy.

Исходные тексты и значения аннотаций в отчёт не включаются. По умолчанию требуются
100% удаления размеченных вхождений и 100% сохранения контрольных фрагментов;
ненулевой exit code блокирует CI/деплой. Точность выводится для анализа; при
необходимости задать `--min-precision`, `--min-recall`, `--min-preservation`.
Пороговые значения находятся в диапазоне от 0 до 1.

Свой корпус передаётся через `--corpus`. Формат примера:

```json
{
  "version": 1,
  "cases": [{
    "id": "declension",
    "text": "Письмо Ивана. Доход 12345 рублей.",
    "identities": [{"value": "Иван", "kind": "participant"}],
    "sensitive": [{"value": "Ивана"}],
    "preserve": ["12345 рублей"]
  }]
}
```

Контрольные имена и номера в Git должны быть вымышленными. Для собственного
закрытого корпуса использовать локальные файлы с ограниченным доступом.
Добавлять найденный дефект синтетическим примером: он станет регрессионной
проверкой. Успех на корпусе не гарантирует анонимность произвольной истории.

CI сохраняет отчёт стандартного синтетического корпуса в artifact
`development-mcp-redaction-quality`, в том числе при неуспешной проверке.

## 5. Сравнение алгоритмов и промптов

### Закрепить выборку

Использовать JSON-файлы из `development_mcp.export`. Например:

```powershell
python -m development_mcp.eval_dataset .tmp/case.json --field core_motivationletter.letter_text --reference core_motivationletter.admin_score=score --output .tmp/fixed-dataset.json
```

Можно передать несколько файлов, повторять `--field` и `--reference`. Контрольный
ответ берётся из указанной записи или единственной непосредственно связанной
записи: например,
`--reference review_by_tutor_interviewresult.interviewer_score=score` для
`review_by_tutor_interview.transcript`. Для вложенного ключа ответа используется
форма `table.field=content.score`. Неоднозначные ссылки и разные версии одного
случая отклоняются. Отсутствующее контрольное значение оставляет пример без метки.

По умолчанию выбирается до 20 непустых текстов не длиннее 100 000 символов;
`--limit` и `--max-characters` задают другие пределы. Текст не обрезается молча.
Порядок примеров стабилен, повторяющиеся примеры исключаются. Зафиксированный JSON
содержит тексты, эталоны, непрозрачные ID, хеши источников, текстов и всего набора.
Изменение текста или эталона требует новой сборки выборки. Оба варианта обработки
получают именно этот файл. Отметка очистки и хеши обеспечивают проверку формата и
целостности; они не доказывают анонимность или правильность эталонной оценки.

### Локальный пример без API

```powershell
python -m development_mcp.evaluation --dataset development_mcp/eval_examples/dataset.json --baseline development_mcp/eval_examples/baseline.json --candidate development_mcp/eval_examples/candidate.json --output .tmp/comparison.json
```

Пример сравнивает два счётчика слов на синтетическом тексте с эталоном. Для своей
логики конфигурация локального обработчика имеет вид:

```json
{"name":"candidate","provider":"python","callable":"my_package.evals:process","options":{}}
```

Сигнатура: `process(text, options) -> dict | str`. Строка должна содержать JSON-объект.
Обработчику не передаются эталонные ответы. Его реализация и конфигурация получают
хеш. Это доверенный локальный Python-код; имя функции не берётся из текста случая.

### Два варианта промпта

В `development_mcp/eval_examples` есть `openai-*.example.json` и два Markdown-промпта.
Скопировать их вместе в свой каталог `.tmp`, указать конкретную модель вместо
`<choose-model>`, отредактировать промпты и использовать их как `--baseline` и
`--candidate`. Пути `prompt_file` считаются относительно конфигурации. SDK OpenAI
доступен в окружении с `requirements.txt`; ключ задаётся через `OPENAI_API_KEY`
или `GPT_TOKEN` в окружении, а не в конфигурации или наборе случаев.

Примеры промптов считают слова. Для проверки оценки мотивационного письма следует
подставить два варианта своей рубрики, возвращающих JSON с ключом `score`, и
подключить осознанно выбранные контрольные оценки. Человеческая оценка тоже может
быть спорной; согласие с ней измеряет совпадение с выбранным эталоном.

OpenAI-адаптер использует существующую настройку клиента проекта, передаёт текст
отдельным пользовательским сообщением и добавляет инструкцию считать его данными.
Вызов [Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)
выполняется с `store=false`, без инструментов, с лимитом `max_completion_tokens`
(по умолчанию 1000), таймаутом 60 секунд и без автоматических повторов. На один
вариант приходится до одного запроса на пример. Поддержка конкретных параметров
зависит от выбранной модели. Закреплены входы и конфигурации; ответы модели могут
различаться между запусками. В отчёте записываются запрошенная и фактически
возвращённые модельные версии.

### Читать результат

Отчёт содержит хеш выборки, хеши конфигураций/промптов/реализации, число ошибок и
валидных JSON-объектов, изменения ответов между успешными парами, время и токены.
При наличии эталонов рассчитываются покрытие эталонных полей, точные совпадения,
число сопоставимых числовых значений и средняя абсолютная ошибка (MAE). Проверять
покрытие вместе с MAE: пропущенные поля не должны выглядеть улучшением.
Различие ответов само по себе не означает улучшения качества.

Отчёт по умолчанию не содержит текстов случаев и полных ответов. Для отдельного
закрытого файла с ответами указать `--save-outputs .tmp/outputs.json`. Существующие
файлы не перезаписываются. Ошибки обработчиков фиксируются без исходных сообщений
исключений. Выборки и ответы остаются данными с ограниченным доступом. CI запускает
только синтетический локальный пример; реальные случаи и платные запросы в него
не включены.
