# Закрытый MCP для разработки

MCP выдаёт реальные случаи основной программы, НТО и семейных доходов через
`stdio` по SSH. Он читает рабочую PostgreSQL отдельной ролью, очищает текст на
сервере и не создаёт копию базы. HTTP-порт отсутствует. Django, его настройки,
сигналы и фоновые работники не загружаются.

**Автоматическая очистка не гарантирует анонимность.** Редкие обстоятельства могут
позволить узнать человека. Очищенные данные остаются доступными только владельцу
SSH-ключа и передаются выбранному им MCP-клиенту, включая используемую им модель.
Сервис очистки не отправляет исходные тексты внешним API.

## Быстрое добавление новых данных

Черновик декларации можно получить командой `manage.py draft_mcp_model app.Model`.
Генератор моделей, контроль качества обезличивания и сравнение алгоритмов/промптов
описаны в [руководстве инструментов разработки](development-mcp-tools.md).

Для обычной связанной модели достаточно **одной декларации в
`development_mcp/schema.py`**. Например, если в Django добавлена модель
`my_study.CandidateComment` с полями `user`, `status`, `text`, `author_name`:

```python
"my_study_candidatecomment": Table(
    output=("status", "text"),
    identities=(("author_name", "person"),),
    loads=(Load("auth_user", "user_id", programs=("main",)),),
    filters=(CaseFilter("has_candidate_comment", "text", "text"),),
),
```

Эта запись задаёт разрешённые поля, словарь персональных данных и способ загрузки:
`candidatecomment.user_id = auth_user.id` внутри текущего случая. Поле связи
добавляется к разрешённым внутренним столбцам автоматически. Текст очищается,
разбивается на страницы и получает непрозрачный ID существующим механизмом.
Новая секция автоматически появляется в `describe_dataset` и SQL выдачи прав.
Загрузчик, MCP-инструменты и механизм очистки менять не нужно.

Другие варианты:

- Запись к письму: `Load("core_motivationletter", "letter_id", programs=("main",))`.
  Связь `links.letter` с непрозрачным ID создаётся автоматически.
- Запись к анкете: `Load("scholar_form_userinfo", "user_info_id")`.
- Ссылка в обратную сторону: `Load("nto_travel_ntoapplication", "id", source_column="campaign_id", programs=("nto",))`.
  Для выдачи такой связи в ответе указать `links=(("campaign_id", "nto_travel_ntocampaign"),)`
  в декларации исходной таблицы.
- Несколько источников: несколько `Load` в одной декларации. Порядок таблиц в
  файле не влияет на загрузку; циклы завершаются, повторные записи не дублируются.
- Для всех направлений убрать `programs`; для ограничения перечислить нужные.
- Для даты рождения указать `age_field="birth_date"`: наружу выйдет `age_group`.
- Для нового обычного поля существующей модели достаточно добавить его в `output`.
  Персональные поля добавляются в `identities` и используются только для очистки.

После изменения:

```bash
python -m development_mcp.schema
python -m unittest discover -s development_mcp/tests -t . -v
python -m development_mcp.grants --update > mcp-grants-update.sql
# Проверить SQL и выполнить под администратором именно рабочей БД:
psql "$ADMIN_DATABASE_URL" -f mcp-grants-update.sql
```

`--update` можно запускать повторно: он синхронизирует права выделенной роли
с текущим реестром, убирает исключённые права и сохраняет пароль, роль и данные.
Все изменения ACL выполняются одной транзакцией. SQL не применяет миграции;
новые таблицы/столбцы должны уже существовать. Не выполнять его под ролью MCP.
Точный набор прав меняется одновременно для всех версий MCP: между применением
ACL и переключением образа старые сеансы могут временно получать отказ доступа.

Деплой также публикует готовый `mcp-grants-update.sql` и `mcp-registry.json` в
GitHub artifact `development-mcp-access-update`. Версия реестра — отпечаток
деклараций; она доступна через `describe_dataset`. Проверить и применить ACL
можно до повторного запуска MCP-деплоя. Административные реквизиты БД в MCP или
GitHub для этого не добавляются.

Валидатор до запуска обнаруживает неизвестные таблицы/поля источника, направления,
неподключённые таблицы и смешение выходных полей с приватными. Тесты сверяют
декларации с `models.py` приложений и запрещают выдачу файлов и технических секретов.
Для новой модели добавить контрольный пример с личными данными; общие тесты уже
проверяют сам механизм подключения. Новая модель Django или новый столбец без
декларации остаются недоступными MCP.

## Интерфейс

- `describe_dataset()` — направления, статусы, разрешённые поля и ограничения.
- `list_cases(program, status?, limit=20, cursor?, filters?)` — непрозрачные ID,
  статусы и краткие признаки без текстов. `program`: `main`, `nto`, `family_income`; статусы перечислены в
  `describe_dataset`. Для основной программы фильтр относится к `form_status`.
- `get_case(case_id, cursor?)` — связанные записи: `items` с `record_id`, `section`,
  `links`, `field`, `value`, `encoding`. Все ID — HMAC, исходные PK не выдаются.
  `links.participant` согласован между направлениями.
- `export_case(case_id, cursor?)` — постраничный экспорт очищенного случая для
  сборки JSON и импорта в локальную БД. Записи в рабочую БД не выполняются.

`get_case` возвращает до 20 элементов поля и до 40 000 символов текста за ответ.
Одно текстовое поле разбивается на части до 10 000 символов. `offset` и
`total_characters` относятся к **очищенному** тексту; соединять части нужно в
порядке выдачи. Составные JSON-поля возвращаются очищенным JSON-текстом
(`encoding=json`); словари представлены массивом пар `key`/`value`, чтобы очистка
ключей не приводила к потере записей при совпадении замен.

Передавайте `next_cursor` без изменений тому же инструменту с теми же параметрами.
Для `get_case` очищенный снимок хранится только в памяти процесса; курсор действует
10 минут, максимум четыре снимка. Истёкшие снимки удаляются при следующем
`get_case` или завершении процесса. После истечения, вытеснения или переподключения получите
случай заново без курсора (`cursor_expired_restart_case`). Исходные тексты в кэше
не сохраняются. Страницы списка читают актуальную БД: при изменении списка между
запросами возможны сдвиги страниц.

Каждый ответ, включая ошибку, содержит `data_as_of`, `redaction_rules_version` и
`automatically_redacted`. Для всех частей одного случая `data_as_of` одинаковый.
Это время чтения, а не гарантия отсутствия персональных данных.

## Поиск нужных случаев

Например, найти кандидата с расшифровкой собеседования и письмом на доработке:

```json
{
  "program": "main",
  "filters": {
    "has_interview_transcript": true,
    "letter_status": "revision"
  },
  "limit": 10
}
```

Дополнительные условия можно сочетать: `"motivation_score": {"min": 3, "max": 5}`,
`"test_count": {"min": 2}`. Все условия, включая верхнеуровневый `status`,
соединяются через **И**. Границы диапазонов включены. В `filters` разрешены только
имена и значения, перечисленные для направления в `describe_dataset`.

| Направление | Доступные фильтры |
|---|---|
| Основная программа | `selection_step`, `has_motivation_letter`, `letter_status`, `motivation_score`, `has_interview_transcript`, `interview_score`, `has_video_transcript`, `test_count`, `staff_note_count` |
| НТО | `has_situation_details`, `criticality`, `motivation_score`, `staff_note_count` |
| Семейные доходы | `family_size`, `document_count`, `income_source_count`, `staff_note_count` |

Фильтры `has_*` принимают строго `true`/`false`. Пустая строка, пробелы, переносы
строк, NULL и отсутствие связанной записи считаются отсутствием текста. Оценки и
количества принимают непустой объект с `min` и/или `max`; количества — целые числа
не меньше нуля. Отсутствующая оценка не соответствует числовому диапазону.
`letter_status` — текущий статус, а не история всех возвратов на доработку.

Каждый элемент списка содержит `features`: наличие текстов, количества записей,
оценки и известные статусы. Для числового поля выводится максимальное из значений,
отличных от NULL, среди связанных записей (ноль учитывается); диапазон применяется
к этому же значению. Статусы возвращаются списком уникальных известных значений;
неизвестный статус заменяется на `unknown`. Счётчики считают уникальные записи,
а не строки соединения. Десятичные оценки могут возвращаться строкой для сохранения
точности. Исходных текстов, имён и исходных ID в сводке нет.

Поиск и расчёт признаков выполняются в PostgreSQL по разрешённым столбцам: Python
не загружает тексты и не запускает распознавание имён для формирования списка.
Чтобы получить содержание, вызвать `get_case` с выбранным ID.

Ответ повторяет нормализованные условия в `applied_filters`. Для следующей
страницы передать те же `program`, `status`, `filters` и полученный `next_cursor`.
Порядок ключей фильтров не имеет значения. При изменении условий или версии
реестра старый курсор отклоняется; начать поиск заново без курсора.

Новый фильтр добавляется в декларацию нужной таблицы:

```python
filters=(
    CaseFilter("has_candidate_comment", "text", "text"),
    CaseFilter("comment_count", "count"),
    CaseFilter("review_score", "number", "score"),
    CaseFilter("review_status", "choice", "status", choices=("draft", "approved")),
),
```

Поля `text`, `score`, `status` должны входить в `output`; фильтрация по приватным
полям запрещена. Фильтр доступен в направлениях, из которых таблица достижима по
`Load`; при необходимости ограничить его через `programs`. Для поиска используется
кратчайший объявленный путь связи от корня случая. В неоднозначных схемах следует
проверить выбранный путь тестом; произвольные условия SQL в реестре не задаются.

## Экспорт случая и воспроизведение локально

Сначала выбрать `case_id` через `list_cases`. Затем на личном компьютере, в
Python-окружении с `development_mcp/requirements.txt`, выполнить:

```powershell
python -m development_mcp.export --ssh putevka-mcp --case-id <CASE_ID> --output .tmp/case.json
```

Каталог `.tmp` должен существовать. CLI подключается по личному SSH-алиасу,
вызывает `export_case`, собирает все страницы и длинные поля в один JSON.
Файл появляется только после полного получения и проверки данных. Существующий
файл не перезаписывается. JSON содержит только разрешённые очищенные поля и
непрозрачные связи. Для JSON-полей сохраняется структура объектов и массивов,
включая пустые контейнеры. Если обезличивание сделало два ключа словаря одинаковыми,
экспорт отклоняется, чтобы не потерять значение. Курсоры `get_case` и `export_case`
разделены; после обрыва/истечения снимка начать экспорт заново.

Для импорта использовать окружение **основного Django-проекта**, а не MCP-контейнер.
Например, в PowerShell можно поднять отдельную локальную SQLite-базу:

```powershell
$env:DEBUG = "true"
$env:DEVELOPMENT_MCP_IMPORT_ENABLED = "true"
$env:DATABASE_URL = "sqlite:///.tmp/mcp-local.sqlite3"
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py import_development_case .tmp/case.json
```

Команда возвращает JSON с `username`, локальным `user_id`, числом записей,
`urls` и `staff_url`. Пользователь создаётся без прав сотрудника и без рабочего
пароля. Для входа задать пароль интерактивно:

```powershell
.\.venv\Scripts\python.exe manage.py changepassword <USERNAME>
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

В том же PowerShell сохраняется настройка `DATABASE_URL`; сайт откроет именно
локальную базу. `staff_url` предназначен для уже существующей локальной учётной
записи сотрудника. Для закрытой тестовой автоматизации можно передать импорту
`--password`; пароль не сохраняется в JSON и не печатается. По умолчанию запись
разрешена только при обоих флагах `DEBUG` и `DEVELOPMENT_MCP_IMPORT_ENABLED`.
Поддерживаются SQLite и локальная PostgreSQL с именем базы, заканчивающимся на
`_dev` или `_test`; удалённые/обычные production-подключения отклоняются.

Повторный импорт того же случая завершается без изменения имеющихся данных.
Для независимой копии использовать `--suffix copy2`. Все записи создаются одной
транзакцией с новыми локальными ID; ошибка откатывает и пользователя, и связанные
объекты. Произвольные поля, модели, исходные PK и ссылки на чужие записи не
принимаются. Новые связанные модели из реестра импортируются общим механизмом;
для обязательных связей с объектами, отсутствующими в экспорте, требуется явный
адаптер — импорт не выбирает произвольную существующую запись.

Сохраняются экспортированные тексты, статусы, оценки, суммы и доступные связи.
Недоступные личные поля заменяются локальными заглушками, дата рождения —
примерной датой внутри возрастной группы. Сезоны, согласия и профили НТО, а также
объекты документов при необходимости создаются тестовыми. Даты сезона локальные,
его `academic_year` получает уникальную тестовую метку. Файлы и видео отсутствуют.
Ограничения страниц по этапам отбора сохраняются: страница может перенаправить
участника на его текущий этап. Эти различия важны при воспроизведении ошибки.

Импорт выполняется без вызова `save()` моделей и сигналов: уведомления и ИИ-задачи
не создаются. Сами локальные фоновые работники и внешние интеграции при разработке
следует держать отключёнными. JSON содержит реальные очищенные истории и остаётся
файлом с ограниченным доступом; `.tmp` уже исключён из Git. Флаг автоматической
очистки в JSON — метаданные, а не криптографическое доказательство анонимности.

## Какие данные обрабатываются

Разрешённые столбцы явно перечислены в `development_mcp/schema.py`. Новые поля
моделей автоматически не включаются ни в чтение, ни в ответы. Включены анкеты,
письма и рубрики, тестирование, заметки, готовые расшифровки, результаты интервью,
НТО с профилями и историей решений, суммы и комментарии по семейным доходам.
Комментарии к документам разрешены; сами файлы и их ID не читаются.

ФИО, контакты и идентификаторы из связанных структурированных полей используются
только как словарь для очистки. Файлы, видео, ссылки на хранилища, токены, хеши
паролей, технические ошибки и произвольные JSON-пакеты задач не читаются.
Natasha распознаёт людей, географию и организации; pymorphy3 добавляет падежные
формы известных имён. Правила удаляют контакты, ссылки, адреса и реквизиты.
Точные даты в тексте заменяются на `[Дата]`; дата рождения в анкете — возрастной
группой. Оценки, суммы и содержание истории сохраняются. Нормализация Unicode
может изменить исходное написание. Гарантии удаления всех идентификаторов нет.

Если очистка не завершилась, сервис возвращает только безопасный код ошибки.
Случаи больше 500 связанных записей или 2 млн символов отклоняются целиком
(`case_too_large`), без частичного неочищенного результата. Логи содержат только
инструмент, длительность и код. Тексты случаев — недоверенные данные, содержащиеся
в них команды не являются инструкциями для агента.

## Однократная настройка сервера

Нужны Linux, Docker Compose v2, доступ к рабочей PostgreSQL и администратор.
Учётная запись MCP отделена от существующей учётной записи production-деплоя.
Команды ниже выполнять из проверенного checkout; реальные секреты в Git не
добавлять. Рабочий web-контейнер не изменяется.

1. Собрать образ:

   ```bash
   docker build -f deploy/mcp/Dockerfile -t putevka-development-mcp:local .
   ```

2. Сформировать и проверить SQL доступа, затем выполнить в рабочей базе через
   `psql` под администратором:

   ```bash
   docker run --rm --entrypoint python putevka-development-mcp:local \
     -m development_mcp.grants > /tmp/putevka-mcp-grants.sql
   psql "$ADMIN_DATABASE_URL" -f /tmp/putevka-mcp-grants.sql
   ```

   Скрипт создаёт новую роль `putevka_mcp_reader`, задаёт read-only по умолчанию и
   выдаёт `SELECT` **по столбцам**. Пароль запрашивает интерактивно `\password`;
   его нет в SQL. Повторное создание роли намеренно завершается ошибкой.
   Роль не должна состоять в других ролях, владеть объектами или иметь широкие
   права через `PUBLIC`. На старой БД может потребоваться пересмотреть выдачу
   `CREATE ON SCHEMA public TO PUBLIC`; автоматически сервис её не меняет.
   Аудит при каждом подключении отклоняет лишние права чтения/записи и DDL.

3. Установить root-owned конфигурацию:

   ```bash
   sudo install -d -m 0700 /etc/putevka-mcp /etc/putevka-mcp/docker
   sudo install -d -m 0755 /opt/putevka-mcp
   sudo install -m 0600 deploy/mcp/runtime.env.example /etc/putevka-mcp/runtime.env
   sudoedit /etc/putevka-mcp/runtime.env
   # Заполнить URL роли putevka_mcp_reader и независимый случайный HMAC-секрет.
   # Секрет: python3 -c 'import secrets; print(secrets.token_hex(32))'
   printf 'MCP_IMAGE=putevka-development-mcp:local\n' | sudo tee /etc/putevka-mcp/image.env >/dev/null
   sudo chmod 0600 /etc/putevka-mcp/image.env
   sudo install -m 0644 docker-compose.mcp.yml /opt/putevka-mcp/docker-compose.mcp.yml
   sudo install -m 0755 deploy/mcp/putevka-mcp-session /usr/local/sbin/putevka-mcp-session
   ```

   `MCP_DOCKER_NETWORK` — существующая сеть, из которой доступна БД (обычно
   `putevka_app`). Для внешней БД использовать проверяемый TLS (`verify-full`),
   при необходимости установить CA в отдельный образ. Секреты приложения,
   `media`, Docker socket и каталог проекта в контейнер не монтируются.

4. Создать SSH-пользователя и установить **свой публичный ключ**:

   ```bash
   sudo useradd --create-home --shell /bin/sh putevka-mcp
   sudo install -d -m 0755 /etc/ssh/authorized_keys
   # personal-mcp.pub — публичный ключ с личного компьютера, не ключ CI-деплоя.
   { printf 'restrict '; cat personal-mcp.pub; } | sudo tee /etc/ssh/authorized_keys/putevka-mcp >/dev/null
   sudo chown root:root /etc/ssh/authorized_keys/putevka-mcp
   sudo chmod 0644 /etc/ssh/authorized_keys/putevka-mcp
   sudo install -m 0440 deploy/mcp/sudoers.example /etc/sudoers.d/putevka-mcp
   sudo visudo -cf /etc/sudoers.d/putevka-mcp
   sudo install -m 0644 deploy/mcp/sshd_config.example /etc/ssh/sshd_config.d/60-putevka-mcp.conf
   sudo sshd -t
   sudo systemctl reload ssh
   ```

   У пользователя не должно быть других sudo-прав или членства в группе `docker`.
   Shell `/bin/sh` нужен sshd для фиксированной команды; произвольная команда
   блокируется `ForceCommand`. И ключ, и sshd отключают TTY и перенаправления.
   Пользователь не может изменять ключи, wrapper, env-файлы или Compose.

5. Проверить образ и до одного реального случая на направление, не выводя тексты:

   ```bash
   sudo docker --config /etc/putevka-mcp/docker compose \
     --env-file /etc/putevka-mcp/runtime.env --env-file /etc/putevka-mcp/image.env \
     -f /opt/putevka-mcp/docker-compose.mcp.yml \
     run --rm --no-deps -T --interactive=false --entrypoint python development-mcp \
     -m development_mcp.smoke --sample-cases
   ```

   Успех: `{"code":"ok","cases_checked":N}`. Ноль случаев означает отсутствие
   случаев в БД, а не проверку реального текста. На ошибке выдаётся только
   `smoke_failed`; проверять схему, настройки и ACL нужно на сервере без публикации
   исходных данных. `sshd -T -C user=putevka-mcp,host=localhost,addr=127.0.0.1`
   позволяет проверить применённые ограничения. `ssh -T` должен запускать только
   MCP, попытка `ssh -N -L ...` — завершаться отказом на forwarding.

## Автодеплой через GitHub Actions

Добавлены два workflow:

- `Development MCP Tests` — тесты с настоящей временной PostgreSQL и сборка образа
  на PR/push при изменении MCP.
- `Deploy Development MCP` — тесты, сборка в CI, передача образа по SSH,
  проверка кандидата на рабочей БД и переключение новых SSH-сеансов на новый образ.
  Запускается вручную или автоматически после успешного `Deploy Production`.

Используются уже существующие настройки environment `production`:
`PROD_DEPLOY_HOST`, `PROD_DEPLOY_USER`, `PROD_DEPLOY_KNOWN_HOSTS` (variables) и
`PROD_DEPLOY_SSH_KEY` (secret). Новые пароли и HMAC-секрет остаются на сервере.
Production deploy-пользователю нужен доступ к Docker и passwordless sudo для
установки root-owned MCP-файлов. Это административный deploy-пользователь,
**не** ограниченный `putevka-mcp`.

После однократной настройки добавить **repository variable** `MCP_ENABLED=true`.
Тогда успешный production-деплой автоматически запускает MCP-деплой той же
ревизии. Ограничения environment `production`, если они настроены в GitHub,
сохраняются. При ручном запуске выбирать ревизию, совместимую со схемой рабочей БД.
Workflow не применяет миграции приложения и не меняет PostgreSQL-права;
он публикует SQL синхронизации ACL отдельным artifact.

Кандидат сначала проходит `smoke --sample-cases`; при провале используемый образ
не переключается. Действующие stdio-сеансы продолжают работу со старым образом;
для обновления нужно переподключить клиент. Предыдущие Compose, wrapper и
`image.env` сохраняются с суффиксом `.previous`. Для отката восстановить все три
файла и переподключиться; старые Docker images автоматически не удаляются.

При изменении allowlist применить проверенный SQL из `grants --update` и выполнить
MCP-деплой. Старые и новые сеансы проверяют точный набор прав: изменение ACL
может потребовать завершения старых сеансов. Не выдавать `SELECT ON ALL TABLES`
или default privileges ради успешного деплоя.

## Подключение клиента и отключение доступа

Настроить SSH alias `putevka-mcp` на личном компьютере: `HostName` рабочего сервера,
`User putevka-mcp`, отдельный `IdentityFile`, `IdentitiesOnly yes`,
`StrictHostKeyChecking yes`, `RequestTTY no`. Ключ сервера заранее проверить и
добавить в `known_hosts`. Не использовать `accept-new` без проверки fingerprint.

В MCP-клиенте выбрать stdio-команду `ssh` с аргументами
`["-T", "-o", "BatchMode=yes", "putevka-mcp"]`. В клиент не передаются секреты БД
или HMAC. Тестовый вызов: `describe_dataset`, затем `list_cases` и `get_case`.

Для Windows OpenSSH передать MCP-процессу `PROGRAMDATA=C:\ProgramData`:
некоторые клиенты очищают окружение, и без этой переменной `ssh.exe` завершается
с кодом 255 ещё до подключения. Для Codex CLI:

```powershell
codex mcp add putevka-development --env "PROGRAMDATA=$env:PROGRAMDATA" -- C:/Windows/System32/OpenSSH/ssh.exe -T putevka-mcp
```

После добавления открыть новый чат или перезапустить клиент, чтобы он загрузил
новую конфигурацию MCP. CLI экспорта передаёт эту переменную автоматически.

Для отключения новых подключений удалить публичный ключ на сервере и установить
`MCP_ENABLED=false`. Для немедленного отзыва также завершить SSH-сеансы пользователя,
остановить только контейнеры с label `com.docker.compose.project=putevka-mcp` и
отключить роль БД (`ALTER ROLE putevka_mcp_reader NOLOGIN`), завершив её существующие
подключения. Ротация HMAC-секрета меняет все непрозрачные ID и курсоры.

## Локальные проверки

```powershell
python -m pip install -r development_mcp/requirements.txt
python -m unittest discover -s development_mcp/tests -t . -v
```

Интеграционные тесты PostgreSQL требуют `MCP_TEST_ADMIN_URL` на **новую пустую
одноразовую** БД `mcp_test` в отдельном кластере. Они создают таблицы и роль,
на рабочую БД их направлять нельзя. Без переменной интеграционные тесты пропускаются.
Проверяются реальные ACL независимо от transaction read-only, отказ лишних прав,
все направления, утечки в ошибках/логах/JSON, склонения имён, длинные тексты,
курсор продолжения, настоящий MCP stdio handshake и недоступность новых полей.

## Направления конкретного сервера

`MCP_PROGRAMS` явно перечисляет установленные направления через запятую.
Текущий production использует `main,family_income`: приложения НТО там пока нет.
В этом профиле MCP не читает таблицы НТО и не выдаёт на них права.
Для сервера с установленным НТО можно указать `main,nto,family_income`.
При изменении профиля повторно сформировать и применить `grants --update` с тем же
`MCP_PROGRAMS`. Для генерации SQL через `docker run` передать
`-e MCP_PROGRAMS=main,family_income`. Compose берёт профиль из `runtime.env`.
При использовании Django инструментов профиль по умолчанию учитывает наличие
приложения НТО в `INSTALLED_APPS`; явная переменная окружения имеет приоритет.
GitHub artifact с SQL использует repository variable `MCP_PROGRAMS`, по умолчанию
`main,family_income`. Полный набор направлений остаётся доступен для тестов сервера
и окружений разработки без Django.
